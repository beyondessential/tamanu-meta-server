# Kubernetes health checks in Canopy — card breakdown

Children spawned from the k8s-health-checks brainstorm. The parent stays the umbrella; these carry the work. Two research spikes came first because their outcomes constrain the implementation, which the specs (see `monitoring/kubernetes.md`) describe at a behavioural level.

**Both spikes have landed** (H1: cluster auth; J1: namespace layout) and reshaped the implementation cards below. H1's decisive outcome is an **in-cluster relay that dials Canopy** rather than Canopy reaching into clusters directly, which adds a new foundational card (the relay itself) and a design card (the relay's method set), and rescopes the harvest to run inside the relay. J1's findings — the positional `facility-<N>` prefix, Gateway API over Ingress, zero-replica duties, TTL hibernation — are carried into the picker and check cards. See `plans/h1/plan.md` and `plans/j1/plan.md`.

Two of H1's to-confirm items need no spike. QUIC over Tailscale is established practice elsewhere in our infrastructure, so the transport is known-good rather than something to prove. And `bestool-alertd` is published and was deliberately built as a library, so embedding it is the expected use of the crate. What remains open about the harvest is its contract with Canopy's filing, not the crate's shape, which the harvest-contract card below carries.

## Research spike: cluster authentication mechanism · H1

Determine how Canopy authenticates to and reads from external Kubernetes clusters, so the implementation can settle its credential storage and connection code. The target clusters are all AWS EKS with OIDC identities; there is one external cluster today and at least one more expected, so the mechanism must support multiple. Canopy also runs in one EKS cluster itself and should be able to read Tamanu instances co-resident there via an in-cluster RBAC policy that reaches beyond its own namespace. Weigh the layer the auth should live at — Kubernetes-level delegation or a tunnel, network-level access, or Canopy owning an OIDC/IAM flow to mint a short-lived per-cluster token and pull directly — against operability and least-privilege read-only access. Output: a chosen mechanism, the RBAC/permissions Canopy needs, and how per-cluster credentials are stored and rotated, feeding the cluster-registration settings page.

## Research spike: Tamanu Kubernetes namespace layout · J1

Map what actually exists in a Tamanu Kubernetes namespace and where, from the perspective of what Canopy needs for its checks and setup. Canopy needs, per namespace (one server group at one rank): the list of central servers and facilities running there for the server-identity picker; each server's workloads by duty (central tasks, central sync, central API replicas, facility processes/tasks) for readiness, crashloop/restart, and resource-pressure checks; the ingress or Gateway resource and front-end API for the liveness check; the PVCs for the storage check; each instance's own Postgres and the CNPG-managed Kubernetes secret backing it for the DB-check harvest; and the facility name/ID/prefix used to locate a facility's databases and containers. The card describes that required-inputs list, then works out where each piece lives in the namespace and how it's labelled or named, so the implementation can query it reliably.

## Harvest contract: alertd checks filed by Canopy · G2

Design card; gates N1 and informs the relay method set. That `bestool-alertd` is embeddable is settled: it is published and was built as a library. What is not settled is the contract between what the library produces in the relay and what Canopy files under the `alertd` source, which is where this design can go quietly wrong. Work out:

- **Filing parity with pushed servers.** K8S requires a Kubernetes server and a pushed server to share one catalog entry and one policy per check. So a harvested filing must match a pushed one in check name and in the detail fields scoped policy rules reach as `check.<field>`; any drift silently splits one operator-configured check into two that grade differently. Establish the mapping from the library's results onto Canopy's filing, and what a push carries that a harvest must supply for itself.
- **Which checks apply.** The alertd suite is not all database-derived. Determine which checks are DB-only and therefore meaningful for a Kubernetes server, whether the library lets a caller select that subset, and how a check that cannot run there is kept from filing as a failure or ageing into broken.
- **Many instances in one process.** A relay runs the harvest against every instance in every namespace it serves, where a VM runs it once against one database. Confirm the library is re-entrant and safe to drive concurrently per instance, with per-instance configuration rather than process-wide state.
- **Threshold configuration.** Where a check's thresholds come from when there is no per-server bestool configuration to read them from.
- **Version skew as check drift.** The point of reusing alertd is that harvested and pushed checks cannot diverge, but a relay pinning one alertd version while servers run another reintroduces divergence as a version difference. Decide how that is bounded, and how it couples to the relay's own protocol versioning.
- **Server figures.** FIG presents a bestool version from what bestool reports in its server-wide detail, and no version where only other sources report. Settle what a Kubernetes server presents, given its alertd checks come from a relay rather than an agent on the server. May need a fold into FIG.

Verifies spec: K8S.

## In-cluster relay and transport

New, from H1; foundation the registry and both check families build on. Build the small Canopy-authored relay that runs in each cluster: it holds the Kubernetes read permissions (a ServiceAccount with `get`/`list`/`watch` over the read set J1 enumerates, no `exec`/`portforward`), connects to each instance's local Postgres, and opens an outbound long-lived connection to Canopy — Canopy never dials the cluster. Transport is QUIC (`quinn`, on the workspace's `aws-lc-rs` rustls provider) over Tailscale, with a kernel-mode Tailscale sidecar at both ends (`NET_ADMIN`, TUN), which is established practice elsewhere in our infrastructure rather than new ground; the relay gets its own namespace. A relay is a device with a new `role`, authenticated by its tailnet peer tag from the QUIC connection, optionally pinning its SPKI fingerprint at enrollment. Includes protocol versioning from the start, since the relay is a second deployable with its own release cycle. Leaves the relay's method set to its own design card. Verifies spec: K8S.

## Relay method set

New design card, from H1; gates M1 and N1. Design the relay's request/response surface, which is the security boundary the relay design exists to create — the relay's methods take the role RBAC plays under direct access, so this warrants one deliberate pass rather than a method accreting per check. Weigh check-shaped (Canopy receives filed results only, tightest surface, a relay release per new check) against resource-shaped (Canopy keeps the check logic and iterates without redeploying relays, but the surface drifts toward an RBAC proxy). Candidate middle to evaluate: resource-shaped for the `kubernetes` infra checks, whose inputs are plain objects, and check-shaped for the `alertd` harvest, where the point is that credentials and query traffic stay in the cluster. This also settles the relay's implementation language. Verifies spec: K8S.

## Cluster registry and connection · K1

Draft, waits on the relay card. Build the in-app cluster registry the specs describe: a settings page where an admin registers a Kubernetes cluster, and adding one tests that the cluster's relay is connected and answering before it is saved. Per H1 a registered cluster is a relay identity and nothing else — Canopy stores no cluster credentials, so there is no secret to encrypt at rest and no rotation to own. The per-server Kubernetes form's cluster picker draws from this registry. Covers both external clusters and the cluster Canopy runs in (whether Canopy's own cluster uses a relay or a widened in-cluster ClusterRole is an open item from H1). Verifies spec: K8S.

## Server Kubernetes identity and picker · L1

Draft, waits on J1. Add the per-server Kubernetes coordinates — cluster, namespace, and for a facility its facility identity — to server create/edit. When an operator marks a server as running on Kubernetes and picks a registered cluster and a namespace, Canopy reads that namespace (through the relay), lists the central servers and facilities running there, and the operator selects which one the record is; that selection becomes the identity the monitoring uses. Per J1 the roster is derived from the CNPG clusters present (`central-db`, `facility-<N>-db`), and a facility's resource prefix `facility-<N>` is a **positional index, not its id or name** — so the picker must join across resource kinds (CNPG cluster ↔ app workloads carrying `app.kubernetes.io/instance` ↔ Gateway listener hostname) and **persist the prefix↔id/host binding**, because neither is derivable from the other. Present a server's Kubernetes coordinates wherever its classification is shown. Depends on the cluster registry for cluster access. Verifies spec: K8S.

## Infrastructure checks (`kubernetes` source) · M1

Draft, waits on the relay method set. A worker that reads a Kubernetes server's cluster and namespace, via the relay, and determines its infrastructure checks under the new `kubernetes` source: server live (Gateway/HTTPRoute plus front-end API `<prefix>-api` answering `GET /`), workloads ready, restarts/crash-looping, database up, storage, and resource pressure. Register the `kubernetes` source as reserved and its checks as already reviewed with sensible policy. Per J1: read expected replicas from each Deployment's own `.spec.replicas` and **do not alarm on a duty deliberately scaled to zero**; query `Gateway`/`HTTPRoute` but **tolerate an un-migrated namespace still on `Ingress`** rather than reading a missing Gateway as "server gone"; storage is the CNPG PVCs (`cnpg.io/cluster: <prefix>-db`) against `Cluster.spec.storage.size`. Decide how a **TTL-hibernated deploy** (present but scaled to zero) is treated — likely broken/unconfirmed rather than failing. Depends on the relay for cluster access and the method set for how it reads objects. Verifies spec: K8S.

## Harvested database checks (`alertd` source) · N1

Draft, waits on the relay method set. Integrate the published `bestool-alertd` crate as a library **inside the relay** (per H1, not a Canopy worker), connect it to each instance's own Postgres — credentials read in-cluster from the CNPG `<prefix>-db-app` secret and dialled at `<prefix>-db-rw`, database `app` (J1), never per-server config and never leaving the cluster — run the Tamanu database-level checks (sync, FHIR, and the rest), and report results up for Canopy to file under the `alertd` source so a Kubernetes server and a pushed server share one catalog entry and policy per check. Reuse the same check implementation so the two never diverge. Depends on the relay (which hosts the harvest) and the method set (check-shaped for the harvest, so credentials and query traffic stay in the cluster). Verifies spec: K8S.

## Reachability and cluster-failure handling · P1

Draft, waits on the source worker. Make a Kubernetes server's reachability Canopy-determined: green by default, failing only when the configured namespace no longer exists. Add the Kubernetes cluster connectivity self-alert (escalating) as one Canopy-wide check with each cluster an instance; per H1 this is driven by **relay liveness** — a relay's dropped connection is the direct signal — so note the diagnosis shifts to "relay not connected", which can mean the relay is down while the cluster is healthy. When a cluster is unreachable, mark its servers' pulled and harvested checks broken without raising them to failures, so an unreachable cluster surfaces through that one check rather than flooding the fleet. Verifies spec: K8S. Verifies spec: SELF. Verifies spec: CHK.
