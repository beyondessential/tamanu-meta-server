Status push wire shapes

Canopy accepts both formats and tells them apart on arrival. A unified push is split Canopy-side; a split push is taken verbatim. bestool moves across one release at a time, and the unified path retires when nothing sends it.

machine-subject application-subject

The two formats

Unified what bestool sends today

POST /status/{server_id} where server_id is really the machine 

{
  "source": "alertd",
  "health": [
    { "check": "tamanu_api",   "result": "passed" },
    { "check": "sync_lag",     "result": "warning",
      "lag_seconds": 412 },
    { "check": "disk_free",    "result": "passed",
      "percent": 37 },
    { "check": "time_sync",    "result": "passed" }
  ],
  "tamanuVersion": "2.33.0",
  "pgVersion": "16.4",
  "nodeVersion": "22.11.0",
  "os": "Ubuntu 22.04",
  "hostname": "nauru-prod-01",
  "timezone": "Pacific/Nauru",
  "bestoolVersion": "0.41.2"
}

One box, one application assumed. Machine and application facts sit in the same health set and the same top level, so Canopy has to know which is which to file them apart. A second workload on this host is a second server record repeating every machine fact.

Split new

POST /status/{machine_id} 

{
  "source": "alertd",
  "machine": {
    "health": [
      { "check": "disk_free", "result": "passed",
        "detail": { "percent": 37 } },
      { "check": "time_sync", "result": "passed" }
    ],
    "detail": {
      "os": "Ubuntu 22.04",
      "hostname": "nauru-prod-01",
      "timezone": "Pacific/Nauru",
      "bestoolVersion": "0.41.2"
    }
  },
  "applications": [
    {
      "id": "9f1c…",
      "health": [
        { "check": "tamanu_api", "result": "passed" },
        { "check": "sync_lag", "result": "warning",
          "detail": { "lag_seconds": 412 } }
      ],
      "detail": {
        "tamanuVersion": "2.33.0",
        "pgVersion": "16.4",
        "nodeVersion": "22.11.0"
      }
    }
  ]
}

The subject is structural, not inferred. Canopy files what it is given. A second workload adds an entry to applications rather than duplicating the machine, which is the case the split exists for.

applications is a list because a machine can carry several; machine is an object because an application has at most one.

Free-form fields nest under detail instead of flattening. Today they are spread at the top level and inside each health entry, so a reporter cannot send a field called source, health, check or result without colliding with the envelope. A container removes the reserved words entirely: anything inside detail is data, and everything outside it is structure.

It also makes the envelope extensible. A new sibling of health and detail can be added later without ambiguity, because the envelope's keys are a closed set rather than whatever a reporter did not happen to send.

detail is Canopy's own word for this already, in the status contract, the check-state model and the figures. Policy rules and the fleet spread reach a check's fields as check.<field>, which is exactly health[].detail.<field>, so the wire and the vocabulary line up rather than needing translation.

Telling them apart

The presence of machine is the discriminator. It is the one key a unified push can never carry, needs no version negotiation, and stays correct if a sender skips releases.

Arriving push Read as What Canopy does
machine present split Files each section against its own target. Splits nothing.
health present, no machine unified Splits by the machine-subject rule below, files against the machine and its single application.
no health legacy Tamanu Unchanged: the tamanu source reporting one passing tasks heartbeat. Retires when its last sender does.

The unified split rule

Canopy holds this list only while unified pushes exist, and it has to agree with what bestool decides in card L2. A unified push from a two-application machine still lands on one application, since the format cannot say which.

Subject Checks Detail fields
machine disk_free, memory, load, time_sync, tailscale os, hostname, timezone, bestoolVersion, uptime
application everything else tamanuVersion, pgVersion, nodeVersion, everything else

Application is the default, machine is the named exception. An unknown check from a new reporter lands on the application, which is where an unknown check belonged before the split, so nothing changes meaning by being unlisted.
