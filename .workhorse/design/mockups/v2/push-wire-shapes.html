Status push wire shapes

Canopy accepts both formats and tells them apart on arrival. A unified push is split Canopy-side; a split push is taken verbatim. bestool moves across one release at a time, and the unified path retires when nothing sends it.

machine-subject application-subject

The two formats

Unified what bestool sends today

POST /status/{server_id} where server_id is really the machine 

{
  "source": "alertd",
  "health": [
    { "check": "tamanu_http",   "result": "passed" },
    { "check": "sync_facility_stale",     "result": "warning",
      "stale_facilities": 3 },
    { "check": "disk_free",    "result": "passed",
      "percent": 37 },
    { "check": "time_sync",    "result": "passed" }
  ],
  "tamanuVersion": "2.33.0",
  "pgVersion": "16.4",
  "nodeVersion": "22.11.0",
  "timezone": "Pacific/Nauru",
  "hostname": "nauru-prod-01",
  "osName": "Ubuntu",
  "osTimezone": "UTC",
  "bestoolVersion": "0.41.2"
}

One box, one application assumed. Machine and application facts sit in the same health set and the same top level, so Canopy has to know which is which to file them apart. A second workload on this host is a second server record repeating every machine fact.

Split new

POST /status/{machine_id} 

{
  "source": "alertd",
  "machine": {
    "health": [
      { "check": "disk_free", "result": "passed",
        "detail": { "percent": 37 } },
      { "check": "time_sync", "result": "passed" }
    ],
    "detail": {
      "hostname": "nauru-prod-01",
      "osName": "Ubuntu",
      "osVersion": "22.04",
      "osTimezone": "UTC",
      "cpuCores": 4,
      "services": ["tamanu-central", "postgresql"],
      "bestoolVersion": "0.41.2"
    }
  },
  "applications": {
    "a1f4c2": {
      "type": "tamanu-central",
      "health": [
        { "check": "tamanu_http", "result": "passed" },
        { "check": "sync_facility_stale", "result": "warning",
          "detail": { "stale_facilities": 3 } }
      ],
      "detail": {
        "tamanuVersion": "2.33.0",
        "tamanuServerKind": "central",
        "canonicalUrl": "https://nauru.example",
        "timezone": "Pacific/Nauru",
        "pgVersion": "16.4",
        "nodeVersion": "22.11.0"
      }
    }
  }
}

The subject is structural, not inferred. Canopy files what it is given. A second workload adds an entry to applications rather than duplicating the machine, which is the case the split exists for.

machine is an object because an application has at most one. applications is an object too, keyed by an identifier the reporter chooses for each application it found.

The key is the reporter's, and Canopy's identifier stays Canopy's. A reporter cannot know what Canopy calls an application, and on a machine's first report there may be nothing to know. So it sends a key of its own, unique on that machine and stable across its pushes, and Canopy correlates on the machine, that key and the type together. What the key is derived from is the reporter's business.

Correlating on the type as well means a reporter that changes an application's type under an unchanged key reads as one application going away and another arriving, which is what it is. The one that went away goes unreachable and alerts; the one that arrived is adopted silently. An operator resolves it by archiving whichever of the two is wrong.

Keying the object rather than listing entries makes that uniqueness a property of the format: a payload with two applications sharing a key cannot be written. type then says what each one is, since the key only says which.

Check names stay bare on the wire. Canopy qualifies them with the type of the application they were filed against, so the catalog entry reads tamanu-central.tamanu_http while the reporter sends tamanu_http. Two types reporting one bare name are two entries. A machine check has no application to qualify it and keeps its bare name.

Free-form fields nest under detail instead of flattening. Today they are spread at the top level and inside each health entry, so a reporter cannot send a field called source, health, check or result without colliding with the envelope. A container removes the reserved words entirely: anything inside detail is data, and everything outside it is structure.

It also makes the envelope extensible. A new sibling of health and detail can be added later without ambiguity, because the envelope's keys are a closed set rather than whatever a reporter did not happen to send.

detail is Canopy's own word for this already, in the status contract, the check-state model and the figures. Policy rules and the fleet spread reach a check's fields as check.<field>, which is exactly health[].detail.<field>, so the wire and the vocabulary line up rather than needing translation.

Telling them apart

The presence of machine is the discriminator. It is the one key a unified push can never carry, needs no version negotiation, and stays correct if a sender skips releases.

Arriving push Read as What Canopy does
machine present split Files each section against its own target. Splits nothing.
health present, no machine unified Splits by the machine-subject rule below, files against the machine and its single application.
no health legacy Tamanu Unchanged: the tamanu source reporting one passing tasks heartbeat. Retires when its last sender does.

The unified split rule

From bestool's registry: 45 checks, 18 machine-subject and 27 application-subject. Canopy only has to hold the machine list, because application is the default, so the rule is an 18-name allowlist rather than a 45-name mapping. It exists only while unified pushes do.

The list is per name, not per prefix, and it has to be. Caddy splits across both grains: caddy_version, caddy_resolvers and caddyfile_version are the install on the box, while caddy_certs is what it serves for one application. A prefix rule would file the certs against the machine and lose which application they belong to.

ips and ips_errors are not the same subject either, or even the same word: one is the machine's addresses, the other is a Tamanu error stream. Two checks sharing a prefix and sharing nothing else is exactly the case a pattern would get wrong silently.

external_users being machine-subject moves operator presence. The status page reads it to show who is logged in (operators_from_health, aggregateOperators), and it currently attributes them to a server. People are on a box rather than in an application, so the machine is the truer home, but the operator marks on the group card change what they are counting.

billing_tags being machine-subject agrees with the model independently. On a VM the cost is incurred by the box, which is why both grains carry billing tags; bestool reached the same answer from the other side.

Two timezones

The detail split puts osTimezone on the machine and timezone on the application, so a fact that was one figure becomes two that can disagree. 

  "machine": {
    "detail": { "osTimezone": "UTC" }
  },
  "applications": {
    "a1f4c2": { "detail": { "timezone": "Pacific/Nauru" } }
  }

A Tamanu configured for one timezone on a box set to another is a real configuration, not a contradiction. The figures today present one timezone, described as the server's own configured timezone so an operator can read its local time. Which one that means now has to be answered: the box's clock, the application's setting, or both side by side with the disagreement visible.

Worth noting that a disagreement is often the thing an operator wants to see, since a timestamp read in the wrong zone is a class of bug that survives a long time.

Fallbacks that now cross grains

Two figure rules reach for a value that has moved to the other grain.

Figure Current fallback After the split
Platform A server reporting no operating system falls back to the family its database engine gives away. The OS is machine-subject and the database engine is application-subject, so a machine with no reported OS has to read its applications' pgVersion to guess.
Runtime version When no source reports it, falls back to the runtime named by the reporting device's connection metadata. The runtime is application-subject and the identity is reached through the machine, so the fallback reads across the link.

Neither is broken, both are now explicit. They read across the machine link rather than within one record, which is fine while an application has at most one machine. Both are worth stating rather than inheriting, because a reader of the figures spec will otherwise assume a figure is sourced from its own grain.
